# Solana IDL Specification v1.0.0

A unified, framework-agnostic description of a Solana program's public interface. An IDL lets tooling generate clients, decoders, documentation, and transaction builders without reading the program source.

This is a redesign, not a patch of [v0.1.0](./v0.1.0.md). See [Migration notes](#16-migration-notes) for the diff. The rationale for every decision is in [`COMPARISON.md`](./COMPARISON.md).

---

## Design principles

Five principles shape every section below. When a rule feels non-obvious, re-read these.

1. **Tagged unions everywhere.** Every union is a JSON object with a `type` field (e.g. `{ "type": "constant", ... }`). No mixed `string | object` unions. The single exception: number-type primitives may appear as bare strings (`"u64"`) as little-endian shorthand — see §10.
2. **Wire layout lives in the type system.** There are no `serialization` or `repr` fields. If a field has a quirk (size-prefix width, endianness, padding, sentinel, fixed size), describe it with a type-node wrapper.
3. **Optional descriptive layers.** Contextual values (§13), semantic formats (§14), instruction summaries (§15), structured remaining-accounts (§5.4), and generics (§10.7) are *optional*. Minimal conformance doesn't require producers to emit them or consumers to understand them.
4. **Inline at point of use.** Values that matter (seeds, discriminator bytes, defaults) live where they're referenced. There's no free-floating `constants` block.
5. **Shared machinery.** [Path expressions](#path-expressions) and [semantic formats](#semantic-formats) are defined once in §11 and reused by `address` (§12), PDA seeds (§9), defaults (§13), and instruction summaries (§15).

## Default omission

Fields annotated with a default value are **omitted from JSON** when they equal that default. Missing fields must be treated as their documented default. Arrays default to `[]`; booleans default to `false`; explicit `null` is only legal where the table says so.

## 3. Multi-program: `additionalPrograms`

`Idl.additionalPrograms` holds peer programs referenced by this IDL. Each entry is a full `Idl` object. Useful when a program CPIs into a peer (SPL Token, Metaplex, a sibling program) and the document should carry enough to build clients without stitching separate IDLs.

A defined-type reference (§10.6) may target a peer program via the `program` field: `{ "type": "defined", "name": "TokenAccount", "program": "spl_token" }` — the name resolves in `additionalPrograms[].metadata.name`.

```json
"additionalPrograms": [
  {
    "address": "TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA",
    "metadata": { "name": "spl_token", "version": "3.5.0", "spec": "1.0.0", "generator": { ... } },
    "accounts": [ { "name": "TokenAccount", "data": { ... } } ]
  }
]
```

## 4. PDAs

PDAs are first-class in v1.0.0. Defined once at the program level, referenced by instructions via [contextual values](#13-contextual-values-optional) and, optionally, by account types via the [`IdlAccount.pda`](#6-accounts) canonical link.

The relationship between PDAs and account types is **many-to-many and fully optional**:

- An account type need not have a backing PDA (a regular keypair-owned account, or one at a known fixed address, omits the `pda` link).
- A PDA need not correspond to an account type (a PDA used as an intermediate derivation, a lamport-holding vault, or a signer authority simply stands alone in `pdas[]` with no account linking back).
- More than one account type may reference the same PDA (unusual but valid).

### `IdlPda`

| Field       | Type                    | Default | Description |
|-------------|-------------------------|---------|-------------|
| `name`      | `string` (camelCase)    | —       | Unique within the IDL; referenced by name. |
| `docs`      | `string[]`              | `[]`    | Documentation. |
| `programId` | `string`                | —       | Deriving program. Omit to use the enclosing `Idl.address`. |
| `seeds`     | [`IdlSeed[]`](#idlseed) | —       | Ordered list of seeds. |

### `IdlSeed`

Tagged union on `"type"`:

| `"type"`      | Fields                                                              | Description |
|---------------|---------------------------------------------------------------------|-------------|
| `"constant"`  | `bytes: number[]`                                                   | Constant byte slice. |
| `"programId"` | _(none)_                                                            | Seed resolves to the enclosing program's address at derivation time. Maps to Codama's `constantPdaSeedNodeFromProgramId()`. |
| `"variable"`  | `name: string`, `valueType: IdlType`, `docs?: string[]`             | Named slot bound at the instruction call site (see §13). |

```json
{
  "name": "counter",
  "seeds": [
    { "type": "constant", "bytes": [99, 111, 117, 110, 116, 101, 114] },
    { "type": "variable", "name": "authority", "valueType": "pubkey" }
  ]
}
```

An instruction account that uses this PDA declares a `{ "type": "pda", "name": "counter", ... }` default (§13); the variable seeds are bound either implicitly (by matching account / argument names) or explicitly via `bindings`.

|----------------------|-----------------------------------------------------------------|---------|-------------|

| `docs`               | `string[]`                                                      | `[]`    | Documentation. |

| `args`               | [`IdlInstructionArg[]`](#53-idlinstructionarg)                  | `[]`    | Ordered argument list. The program's discriminator bytes appear as leading [`constant`](#9-dispatch-and-constant-fields) fields in this list. |
| `returns`            | [`IdlType`](#10-type-system)                                    | —       | Return-data type. |

| `byteDeltas`         | [`IdlByteDelta[]`](#57-byte-deltas)                            | `[]`    | Declared account-size changes (rent calculation aid). See [§5.7](#57-byte-deltas). |

### 5.2 `IdlInstructionAccount`

Account entries are flat. Composite grouping (if needed for UX) is reconstructed from the optional `group` tag.

| Field           | Type                                                | Default | Description |
|-----------------|-----------------------------------------------------|---------|-------------|
| `name`          | `string` (camelCase)                                | —       | Account name. Dot-separated when the account comes from a group: `tokenAccounts.mint`. |
| `docs`          | `string[]`                                          | `[]`    | Documentation. |
| `writable`      | `boolean`                                           | `false` | Account will be written to. |
| `signer`        | `boolean`                                           | `false` | Account must sign the Solana transaction. Mutually exclusive with `messageSigner`. |
| `signerOptional` | `boolean`                                          | `false` | Account *may* be a tx signer — the program accepts either a signer or non-signer. Codama parity for `isSigner: "either"`. When `signer` is false and `signerOptional` is true, the account is tolerated in either state. |
| `messageSigner` | [`IdlMessageSigner`](#56-message-signers)           | —       | When present, this account authorizes the instruction by ed25519-signing the rendered bytes of the contained `template` (see [§5.6](#56-message-signers)). Presence alone declares the role — no separate boolean flag. Requires `expiresAt` when present. Mutually exclusive with `signer: true`. |
| `optional`      | `boolean`                                           | `false` | Account may be omitted by the client. |
| `address`       | [`IdlAddressExpression`](#12-address-expressions)   | —       | Enforced address. Either a fixed pubkey or a path to another account's field. |
| `default`       | [`IdlDefaultValue`](#13-contextual-values-optional) | —       | Client-resolution hint. Producers may emit, consumers may ignore. |
| `group`         | `string`                                            | —       | Composite-group label for UX reconstruction. |
| `expiresAt`     | [`IdlPathExpression`](#idlpathexpression)           | —       | Path to the signature expiry value (signed integer, unix seconds). Required when `messageSigner` is present. Resolved per-invocation and embedded in the signed preamble. |

Example — an authority account constrained to equal `counter.authority`:

```json
{
  "name": "authority",
  "signer": true,
  "address": { "type": "field", "path": "counter.authority" }
}
```

### 5.3 `IdlInstructionArg`

| Field                  | Type                                                | Default     | Description |
|------------------------|-----------------------------------------------------|-------------|-------------|
| `name`                 | `string` (camelCase)                                | —           | Argument name. |
| `docs`                 | `string[]`                                          | `[]`        | Documentation. |
| `type`                 | [`IdlType`](#10-type-system)                        | —           | Wire type. |
| `default`              | [`IdlDefaultValue`](#13-contextual-values-optional) | —           | Client-resolution hint. |
| `defaultValueStrategy` | `"omitted" \| "optional"`                            | `"omitted"` | Only meaningful when `default` is present. `omitted` — the arg is always filled by the default; clients don't see it. `optional` — clients may override; default is the fallback. Matches Codama's `defaultValueStrategy`. |

### 5.4 Remaining accounts

`remainingAccounts` is a list of descriptors, each describing a span of trailing accounts. Presence of any entry signals that the instruction accepts trailing accounts; entries may include a `value` sourcing them from an argument or resolver (Codama's `InstructionRemainingAccountsNode` semantics). An absent `remainingAccounts` field means the instruction does not accept trailing accounts.

### `IdlRemainingAccountsEntry`

| Field            | Type                                                | Default | Description |
|------------------|-----------------------------------------------------|---------|-------------|
| `value`          | [`IdlDefaultValue`](#13-contextual-values-optional) | —       | Source of the accounts — typically an `{ type: "argument", ... }` pointing at a `Vec<Pubkey>` arg, or a `{ type: "resolver", ... }`. Absent means "arbitrary accounts appended; shape unspecified." |
| `writable`       | `boolean`                                           | `false` | Whether each account in the span is writable. |
| `signer`         | `boolean`                                           | `false` | Whether each account must sign. |
| `signerOptional` | `boolean`                                           | `false` | Whether each account *may* be a signer (tri-state — Codama parity). |
| `optional`       | `boolean`                                           | `false` | Whether the span may be empty. |
| `docs`           | `string[]`                                          | `[]`    | Documentation. |

Example — Memo program's `addMemo` takes a trailing list of signer accounts sourced from an arg:

```json
"remainingAccounts": [{
  "value": { "type": "argument", "path": "signers" },
  "signer": true,
  "optional": true
}]
```

### 5.5 Pre/post instructions

`preInstructions` / `postInstructions` let an IDL declare setup/teardown the client should splat into the enclosing transaction — avoiding runtime CPIs and shrinking program binary. Entries come from an **open registry** of named operations; v1.0.0 ships one entry (`createAtaIdempotent`). Additional entries land via future RFCs; consumers that don't recognize a registry entry must refuse to build the transaction.

### `IdlPrePostIx`

Tagged union on `"type"`. Each registry entry defines its own fields. Every field of every registry entry is an [address expression](#12-address-expressions) so it can reference parent-instruction accounts or constants.

#### `createAtaIdempotent`

Run the Associated Token Account program's `createIdempotent` instruction.

| Field   | Type                                              | Description |
|---------|---------------------------------------------------|-------------|
| `mint`  | [`IdlAddressExpression`](#12-address-expressions) | Mint the ATA is for. |
| `owner` | [`IdlAddressExpression`](#12-address-expressions) | Owner of the ATA. |
| `payer` | [`IdlAddressExpression`](#12-address-expressions) | Who pays the rent. |

```json
{
  "type": "createAtaIdempotent",
  "mint":  { "type": "field",    "path": "pool.mint" },
  "owner": { "type": "field",    "path": "user.address" },
  "payer": { "type": "constant", "value": "Fg6PaFpoGXkYsidMpWTK6W2BeZ7FEfcYkg476zPFsLnS" }
}
```

### 5.6 Message signers

An account authorizes an instruction in one of two ways: by signing the enclosing Solana transaction (`signer: true`) or by ed25519-signing an intent message off-chain (the `messageSigner` field present). Never both. The program reconstructs each message signer's expected bytes from the instruction's accounts and arguments and verifies the signature via the ed25519 sigverify precompile. This defends against blind signing: a message signer authorizes a specific human-readable intent from its own perspective, not a raw transaction blob.

### `IdlMessageSigner`

The value of the `messageSigner` field on an [`IdlInstructionAccount`](#52-idlinstructionaccount). **Presence of the field — not a separate boolean — declares the account as a message signer.**

| Field          | Type                                                      | Default | Description |
|----------------|-----------------------------------------------------------|---------|-------------|
| `template`     | `string`                                                  | —       | English template with `{placeholder}` tokens. The exact bytes ed25519-signed by this account, wrapped in the preamble below. |
| `placeholders` | `{ [name: string]: IdlMessageSignerPlaceholder }`         | —       | Declares each `{name}` token used in the template. |

### `IdlMessageSignerPlaceholder`

| Field    | Type                      | Default              | Description |
|----------|---------------------------|----------------------|-------------|
| `from`   | `IdlPathExpression`       | —                    | Where the value comes from. |
| `format` | `IdlSemanticFormat`       | `{ "type": "raw" }`  | How to render it. |

#### Multiple message signers

Usually an instruction has just one message signer. Where there are several, each signs its own template independently — different roles may legitimately see different things:

```
maker.messageSigner.template:  "Sell {amountOut} for {amountIn} to {taker}"
taker.messageSigner.template:  "Buy {amountOut} for {amountIn} from {maker}"
```

Both signatures authorize the same on-chain swap, but each signer sees the trade from their own side. There is no instruction-level "canonical template" — the authorization is per signer.

An instruction with one or more `messageSigner` accounts requires one ed25519 sigverify precompile instruction per such account in the enclosing transaction. The program rejects the instruction if an expected signature is missing or doesn't verify against the expected bytes.

#### Authorization model

`signer: true` and a present `messageSigner` are mutually exclusive. The three valid states per account:

| `signer` | `messageSigner` | Behavior |
|---------|-----------------|---------|
| `true`  | absent          | Tx signer. Authorizes by signing the Solana transaction. |
| `false` | present         | Message signer. Authorizes by ed25519-signing the rendered `template` bytes; not a tx signer. |
| `false` | absent          | Not a signer. |

If a role needs both a tx fee payer and an intent signer, model them as *two* separate accounts.

Validation:

- Every `{name}` token in `template` must have an entry in `placeholders` — orphan tokens are a validation error.
- A present `messageSigner` requires `expiresAt` on the same account.
- `messageSigner` present and `signer: true` together is invalid.
- Templates are **English-only**. Clients that need localized UX apply their own translation layer; the signing contract depends on a single pinned string.

#### Signed byte layout (domain separation)

Taking inspiration from [EIP-712](https://eips.ethereum.org/EIPS/eip-712): the bytes a message signer actually signs are not just the rendered template — they include a deterministic **domain preamble** that prevents cross-program, cross-version, and replay-after-expiry attacks. The preamble is derived from the IDL and the invocation; producers do not write it, consumers/verifiers generate it.

```
Solana Signed Intent v1
Program: <Idl.address in base58>
Version: <Idl.metadata.version>
Expires: <ISO 8601 UTC of the resolved expiresAt value>

<rendered messageSigner.template>
```

Rules:

- Lines are separated by single `\n` (LF); no carriage returns.
- Exactly one blank line (`\n\n`) separates the preamble from the rendered template.
- No trailing newline after the rendered template.
- UTF-8 encoded.
- The client **must** display the entire signed payload (including the preamble) to the user — what you see is what you sign.
- The program must reconstruct the same bytes byte-for-byte when verifying.

The `Expires` line is derived from the message signer's `expiresAt` path expression. The resolved value is a signed integer interpreted as unix seconds and rendered in ISO 8601 UTC with seconds precision (e.g. `2026-06-30T23:59:59Z`). The program rejects the signature if the current on-chain `Clock.unix_timestamp` is at or past this instant, independent of signature verification — expired signatures fail fast.

Unlike literal EIP-712, the signed content is human-readable text rather than a structured hash. This deliberately prioritizes WYSIWYS: the preamble gives domain separation without sacrificing readability.

#### Canonical rendering rules

The rendered template is built by substituting each `{name}` token in the signer's `messageSigner.template` with a **canonical rendering** of the placeholder's resolved value. Rendering is deterministic and cross-implementation-identical so signing and verification agree byte-for-byte:

| `format.type`     | Canonical rendering |
|-------------------|----------------------|
| `raw` (or absent) | The value's JSON primitive stringification: integers/bools as-is; floats as `%g` without exponent-form unless unavoidable; strings unquoted; bytes as `0x`-prefixed lowercase hex. |
| `amount`          | `<shifted-decimal-string>` followed by `" "` + `symbol` when `symbol` is declared. Decimals always emitted in full (no trailing-zero trimming). Example: raw `1000000`, decimals `6`, symbol `USDC` → `"1.000000 USDC"`. |
| `solAmount`       | `"<lamports> lamports"`. Lamports integer is rendered without conversion to SOL to avoid float-precision divergence. |
| `dateTime`        | ISO 8601 UTC. `"seconds"` → `YYYY-MM-DDTHH:MM:SSZ`; `"milliseconds"` → `YYYY-MM-DDTHH:MM:SS.sssZ`. |
| `pubkey`          | Full base58-encoded 32-byte pubkey. `truncate` is **ignored** when rendering for a message signature (full form always signed; UI may still truncate when rendering the same placeholder for non-signing display). |

Worked example — for a signer with `messageSigner.template` of `"Transfer {amount} from {source} to {destination}"`, program address `Fg6PaFpo...`, program version `1.2.0`, `expiresAt` resolving to `1782432000` (unix seconds), `amount` → `1000000` (decimals 6, symbol USDC), `source` → `Fg6PaFpo...`, `destination` → `Ah8...`, the exact signed bytes are:

```
Solana Signed Intent v1
Program: Fg6PaFpoGXkYsidMpWTK6W2BeZ7FEfcYkg476zPFsLnS
Version: 1.2.0
Expires: 2026-06-25T00:00:00Z

Transfer 1.000000 USDC from Fg6PaFpoGXkYsidMpWTK6W2BeZ7FEfcYkg476zPFsLnS to Ah8...
```

Changes to `messageSigner.template` (wording, spacing, punctuation) are breaking changes for message-signing clients, same as changing a function signature. Bumping `metadata.version` invalidates all previously-issued signatures for the program — intentional, to force upgrades when the signing contract changes.

### 5.7 Byte deltas

Declares how much an instruction grows or shrinks the size of an account. Lets generated clients compute the lamports needed to re-fund rent when an account reallocates. Maps directly to Codama's `InstructionByteDeltaNode`.

### `IdlByteDelta`

| Field        | Type                                                | Default | Description |
|--------------|-----------------------------------------------------|---------|-------------|
| `value`      | [`IdlDefaultValue`](#13-contextual-values-optional) | —       | The delta. Typically a `constant` (static value), an `argument` (reads the delta from an arg), or a `resolver` (client-computed). Negative values indicate shrink. |
| `withHeader` | `boolean`                                           | `false` | Whether to include the account header (32 bytes of key + flags) in the delta. |
| `docs`       | `string[]`                                          | `[]`    | Documentation. |

```json
// static: Address-Lookup-Table createLookupTable reserves 56 bytes
"byteDeltas": [{
  "value": { "type": "constant", "value": 56, "valueType": "u64" },
  "withHeader": true
}]
```

```json
// argument-driven: SystemProgram createAccount uses the `space` arg
"byteDeltas": [{
  "value": { "type": "argument", "path": "space" },
  "withHeader": true
}]
```

```json
// resolver-driven: extendLookupTable's delta depends on a client calc over `addresses`
"byteDeltas": [{
  "value": {
    "type": "resolver",
    "name": "resolveExtendLookupTableBytes",
    "dependsOn": [{ "type": "argument", "path": "addresses" }]
  }
}]
```

## 6. Accounts

Unlike v0.1.0, account types carry their data layout **inline** — there is no name-matching hop into `types[]`. Only `name` is required; everything else is optional so the shape accommodates regular keypair-owned accounts, PDA-backed accounts, bare lamport holders, and externally-identified accounts in the same schema.

### `IdlAccount`

| Field            | Type                                           | Default | Description |
|------------------|------------------------------------------------|---------|-------------|
| `name`           | `string` (PascalCase)                          | —       | Account type name. |
| `docs`           | `string[]`                                     | `[]`    | Documentation. |
| `data`           | [`IdlTypeStruct`](#106-structs)                | —       | Inline struct. A byte-discriminator, if any, is a leading [`constant`](#9-dispatch-and-constant-fields) field in `data.fields`. Omit `data` entirely for bare lamport holders with no structured payload. |
| `pda`            | `string`                                       | —       | Canonical top-level PDA that produces this account. Omit when the account is not PDA-backed. Documentation-only — the linked PDA in `Idl.pdas[]` drives derivation. |
| `size`           | `number`                                       | —       | Fixed byte size. Also the **size-based discriminator** for programs that dispatch on account length (e.g. SPL Token's 82/165/355 split). Consumers match on `size` before attempting byte discrimination. |

```json
{
  "name": "Counter",
  "pda": "counter",
  "data": {
    "type": "struct",
    "fields": [

      { "name": "count",     "type": "u64" },
      { "name": "bump",      "type": "u8" }

  }
}
```

## 9. Dispatch and constant fields

There is **no separate `discriminators` field** on instructions, accounts, or events. A discriminator is just a constant-valued byte sequence at a specific position on the wire — that's modeled directly as a field whose type is [`IdlTypeConstant`](#idltypeconstant) inside `args` (for instructions) or `data.fields` (for accounts/events).

This unifies dispatch with layout: every byte on the wire is a field, including the ones that are always the same. Multi-layer dispatch (parent byte + enum tag) is just multiple leading constant fields. Field-value dispatch (enum tag at some offset) is a typed field that happens to have a constrained value — producers pre-encode the variant's bytes into a constant field.

### `IdlTypeConstant`

```json
{ "type": "constant", "bytes": [175, 175, 109, 31, 13, 152, 155, 237] }
```

| Field   | Type       | Default | Description |
|---------|------------|---------|-------------|
| `bytes` | `number[]` | —       | The exact bytes written/read at this position. The consumer **must** verify these bytes match on decode; a mismatch means the data doesn't belong to this type. |

Unlike [`padding`](#padding) (which consumes bytes without constraining them), `constant` fields both consume AND constrain. Producers typically give these fields names starting with `_disc` or `_magic` so generated clients can hide them — they're never set by the caller.

### Instruction dispatch

A plain Anchor instruction with an 8-byte SHA-256 discriminator:

```json
"args": [
  { "name": "_disc",  "type": { "type": "constant", "bytes": [11, 18, 104, 9, 104, 174, 59, 33] } },
  { "name": "amount", "type": "u64" }
]
```

A Quasar-style 1-byte developer-assigned discriminator: just a shorter `bytes` array.

**Per-variant dispatch** (Codama's `createSubInstructionsFromEnumArgsVisitor` pattern) — each enum variant is its own top-level [`IdlInstruction`](#51-idlinstruction) with a parent byte + variant byte as two leading constant fields:

```json
// delegateStandardV1
"args": [
  { "name": "_disc",    "type": { "type": "constant", "bytes": [44] } },
  { "name": "_variant", "type": { "type": "constant", "bytes": [0] } },
  ...variant fields...
]

// delegateTransferV1
"args": [
  { "name": "_disc",    "type": { "type": "constant", "bytes": [44] } },
  { "name": "_variant", "type": { "type": "constant", "bytes": [1] } },
  ...variant fields...
]
```

Wire-identical to `[parent_byte, variant_byte, ...variant_fields]`. No shared "parent instruction" to expand, no special sub-instruction machinery — every variant is just a regular top-level instruction whose leading bytes happen to match in the parent position.

**Field discriminators at arbitrary offsets** — when the dispatching field sits after other fields on the wire, just put the constant at that position:

```json
"args": [
  { "name": "header", "type": { "type": "defined", "name": "Header" } },
  { "name": "_tag",   "type": { "type": "constant", "bytes": [3] } },
  { "name": "data",   "type": "u64" }
]
```

The consumer decodes fields in order and verifies the constant bytes as they pass. Mismatches are dispatch failures, not parse errors.

### Account dispatch

Account byte discriminators work the same way — the constant is just the first field of `data`:

```json
"data": {
  "type": "struct",
  "fields": [
    { "name": "_disc",     "type": { "type": "constant", "bytes": [255, 176, 4, 245, 188, 253, 124, 25] } },
    { "name": "authority", "type": "pubkey" }
  ]
}
```

### Size dispatch

Some programs (SPL Token's mint/token/multisig) dispatch on total account length rather than byte content. There's no positional byte to pin, so size dispatch uses the existing [`IdlAccount.size`](#6-accounts) field — consumers match on account length before attempting byte-level decoding:

```json
"accounts": [
  { "name": "Mint",     "size":  82, "data": { ... } },
  { "name": "Token",    "size": 165, "data": { ... } },
  { "name": "Multisig", "size": 355, "data": { ... } }
]
```

## 10. Type system

### 10.1 Primitives — bare strings

Bare-string primitives imply **little-endian** encoding where applicable.

| Value       | Description |
|-------------|-------------|
| `"bool"`    | Boolean (1 byte). |
| `"u8"`, `"i8"`, `"u16"`, `"i16"`, `"u32"`, `"i32"`, `"u64"`, `"i64"`, `"u128"`, `"i128"`, `"u256"`, `"i256"` | Little-endian signed/unsigned integers. |
| `"f32"`, `"f64"` | Little-endian IEEE 754 floats. |
| `"shortU16"` | Solana's compact-u16 (1–3 bytes). |
| `"pubkey"`  | 32 bytes. |
| `"bytes"`   | Variable-length byte array, u32-LE length-prefixed (shorthand; use §10.2 for other prefix widths). |
| `"string"`  | UTF-8 string, u32-LE length-prefixed (shorthand; use §10.2 for other encodings / prefix widths). |

This is the **only** place the spec permits a bare-string form. Everywhere else, unions are tagged objects.

### 10.2 Explicit number types

For non-LE integers or when you need to be explicit:

```json
{ "type": "number", "format": "u64", "endian": "be" }
```

| Field    | Type                                                              | Default | Description |
|----------|-------------------------------------------------------------------|---------|-------------|
| `type`   | `"number"`                                                        | —       | Tag. |
| `format` | `"u8"`..`"i256"`, `"f32"`, `"f64"`, `"shortU16"`                  | —       | Numeric format. |
| `endian` | `"le"` \| `"be"`                                                  | `"le"`  | Byte order. |

### 10.3 Containers

All containers are tagged on `"type"`.

#### Option

```json
{ "type": "option", "value": "u64" }
```

| Field   | Type      | Description |
|---------|-----------|-------------|
| `value` | `IdlType` | Wrapped type. |

#### Array

```json
{ "type": "array", "value": "u8", "count": { "type": "fixed", "value": 32 } }
```

| Field   | Type                                      | Default                                       | Description |
|---------|-------------------------------------------|-----------------------------------------------|-------------|
| `value` | `IdlType`                                 | —                                             | Element type. |
| `count` | [`IdlArrayCount`](#105-array-count-nodes) | `{ "type": "prefixed", "prefix": "u32" }`     | How the count is encoded. |

> **Note.** The default is `{ "type": "prefixed", "prefix": "u32" }` so `{ "type": "array", "value": "u8" }` (with no count) equals Borsh-style `Vec<u8>`. This replaces v0.1.0's separate `vec` vs `array` container forms.

#### String

```json
{ "type": "string", "encoding": "utf8", "count": { "type": "prefixed", "prefix": "u32" } }
```

| Field      | Type                                      | Default                                       | Description |
|------------|-------------------------------------------|-----------------------------------------------|-------------|
| `encoding` | `"utf8"` \| `"base58"` \| `"base64"`       | `"utf8"`                                     | Byte-level encoding. |
| `count`    | [`IdlArrayCount`](#105-array-count-nodes) | `{ "type": "prefixed", "prefix": "u32" }`     | How the length is encoded. |

#### Bytes

```json
{ "type": "bytes", "count": { "type": "prefixed", "prefix": "u16" } }
```

#### Map / Set

```json
{ "type": "map", "key": "pubkey", "value": "u64", "count": { "type": "prefixed", "prefix": "u32" } }
{ "type": "set", "value": "pubkey", "count": { "type": "remainder" } }
```

#### Tuple

```json
{ "type": "tuple", "elements": ["pubkey", "u64"] }
```

#### Padding

```json
{ "type": "padding", "bytes": 7 }
```

| Field   | Type      | Default | Description |
|---------|-----------|---------|-------------|
| `bytes` | `number`  | —       | Fixed number of ignored bytes. |

A `padding` field consumes `bytes` bytes on the wire but is **not** surfaced in the decoded representation. Used to describe non-Borsh struct layouts — see [§10.6.1](#1061-layout-conventions).

#### Boolean (explicit size)

```json
{ "type": "boolean", "size": { "type": "number", "format": "u32" } }
```

| Field  | Type                                | Default | Description |
|--------|-------------------------------------|---------|-------------|
| `size` | [`IdlTypeNumber`](#102-explicit-number-types) | —       | Integer type used to store the boolean on the wire. |

The `"bool"` primitive (§10.1) is equivalent to `{ "type": "boolean", "size": { "type": "number", "format": "u8", "endian": "le" } }`. Use the object form when a program stores booleans as u16/u32/u64 — common in zero-copy structs that align to wider integers.

### 10.4 Layout wrappers

These wrappers describe wire-layout details that can't be captured by a plain type alone: fixed-size slots, hidden framing bytes, offsets, sentinel-terminated sequences, zeroable options, and byte-length prefixes. Each wraps an inner [`IdlType`](#10-type-system) and is wire-transparent to consumers that don't need the detail — the decoded shape matches the inner type unless noted.

All wrappers are tagged on `"type"`.

#### Fixed size

```json
{ "type": "fixedSize", "value": "string", "size": 32 }
```

| Field   | Type      | Default | Description |
|---------|-----------|---------|-------------|
| `value` | `IdlType` | —       | Wrapped type. |
| `size`  | `number`  | —       | Fixed total byte size. The wrapped type's wire bytes are padded with zeros to reach `size` (or truncated if longer — an error in most producers). |

Use for zero-copy accounts that reserve a slot of fixed bytes for a variable-length logical value (e.g. a 32-byte name field regardless of actual string length).

#### Hidden prefix

```json
{ "type": "hiddenPrefix", "value": "string", "prefix": [1, 0, 0, 0] }
```

| Field    | Type       | Default | Description |
|----------|------------|---------|-------------|
| `value`  | `IdlType`  | —       | Wrapped type. |
| `prefix` | `number[]` | —       | Bytes written/read before the wrapped type. Not surfaced in the decoded representation. |

Use for version prefixes and magic bytes — e.g. a Metaplex Token Metadata account that starts with a `key` byte discriminator followed by the real data.

#### Hidden suffix

```json
{ "type": "hiddenSuffix", "value": "string", "suffix": [0] }
```

| Field    | Type       | Default | Description |
|----------|------------|---------|-------------|
| `value`  | `IdlType`  | —       | Wrapped type. |
| `suffix` | `number[]` | —       | Bytes written/read after the wrapped type. Not surfaced. |

#### Pre-offset

```json
{ "type": "preOffset", "value": "u64", "offset": 16, "strategy": "padded" }
```

| Field      | Type                                      | Default      | Description |
|------------|-------------------------------------------|--------------|-------------|
| `value`    | `IdlType`                                 | —            | Wrapped type. |
| `offset`   | `number`                                  | —            | Byte offset. |
| `strategy` | `"padded" \| "absolute" \| "preOffset"`    | `"padded"`   | Interpretation of `offset`: `padded` = skip `offset` bytes (zero-padded on write) from the current position; `absolute` = seek to byte `offset` from buffer start; `preOffset` = rewind `offset` bytes relative to the position before the wrapper started reading. |

Use for reading fields at known absolute positions inside an account (common in fixed-layout zero-copy accounts with reserved regions).

#### Post-offset

```json
{ "type": "postOffset", "value": "pubkey", "offset": 8, "strategy": "padded" }
```

Same fields and strategy vocabulary as `preOffset`. Applies `offset` **after** reading the wrapped type.

#### Sentinel

```json
{ "type": "sentinel", "value": { "type": "string", "encoding": "utf8", "count": { "type": "remainder" } }, "sentinel": [0] }
```

| Field      | Type       | Default | Description |
|------------|------------|---------|-------------|
| `value`    | `IdlType`  | —       | Wrapped type, typically a `string`, `bytes`, or `array` with `count: { "type": "remainder" }`. |
| `sentinel` | `number[]` | —       | Terminator byte sequence consumed on the wire but not included in the decoded value. |

Use for null-terminated C-style strings and sentinel-terminated sequences.

#### Zeroable option

```json
{ "type": "zeroableOption", "value": "pubkey" }
{ "type": "zeroableOption", "value": "u64", "zeroValue": [255, 255, 255, 255, 255, 255, 255, 255] }
```

| Field       | Type       | Default                   | Description |
|-------------|------------|---------------------------|-------------|
| `value`     | `IdlType`  | —                         | Wrapped type. Must be fixed-size. |
| `zeroValue` | `number[]` | all zero bytes, sized to the wrapped type | Byte pattern representing `None`. |

Unlike plain [`option`](#option) which prefixes a 1-byte discriminant, `zeroableOption` uses a sentinel byte pattern (default: all zeros) to indicate `None`. Common in zero-copy Solana programs that pre-allocate fields without discriminant bytes.

#### Remainder option

```json
{ "type": "remainderOption", "value": "u64" }
```

| Field   | Type      | Default | Description |
|---------|-----------|---------|-------------|
| `value` | `IdlType` | —       | Wrapped type. |

Presence is inferred from remaining bytes: if the buffer has enough bytes to read the wrapped type, it's `Some`; otherwise `None`. Used for trailing fields in extensible accounts that older on-chain data doesn't include.

#### Size prefix

```json
{ "type": "sizePrefix", "value": "string", "prefix": { "type": "number", "format": "u32" } }
```

| Field    | Type              | Default | Description |
|----------|-------------------|---------|-------------|
| `value`  | `IdlType`         | —       | Wrapped type. |
| `prefix` | `IdlTypeNumber`   | —       | Number type carrying the byte-length of the wrapped type. |

Unlike the [`count: { "type": "prefixed" }`](#105-array-count-nodes) hint on array/string/bytes (which prefixes an *element* count), `sizePrefix` wraps any type and prefixes the wrapped type's total **byte** length. Useful for length-prefixed arbitrary payloads (SPL Token-2022 extensions, signed-message envelopes).

### 10.5 Array count nodes

Tagged union on `"type"`. Reused by `array`, `string`, `bytes`, `map`, `set`.

| `"type"`     | Fields                                                            | Description |
|--------------|-------------------------------------------------------------------|-------------|
| `"prefixed"` | `prefix: "u8" \| "u16" \| "u32" \| "u64" \| "shortU16"`           | Length written before the data. |
| `"fixed"`    | `value: number`                                                   | Statically known count. |
| `"remainder"`| _(none)_                                                          | Count is whatever bytes remain in the containing buffer. |


#### 10.6.1 Layout conventions

Struct fields are laid out on the wire in declaration order. **No implicit padding is inserted.** This matches Borsh's packed layout natively, including the `repr(packed)` / `repr(C, packed)` subset of zero-copy.

For layouts that do have padding (`repr(C)`, standard bytemuck `Pod` structs), producers emit explicit [`padding`](#padding) fields between data fields:

```json
// Rust: #[repr(C)] struct Foo { flag: u8, value: u64 }
// On BPF: 1 byte flag + 7 pad + 8 value = 16 bytes total
{
  "type": "struct",
  "fields": [
    { "name": "flag",  "type": "u8" },
    { "name": "_pad0", "type": { "type": "padding", "bytes": 7 } },
    { "name": "value", "type": "u64" }
  ]
}
```

Trailing padding (for struct-level alignment under `repr(C)`) is emitted as a final `padding` field. `IdlAccount.size` may be set to the total on-wire size as a cross-check.

Guidance for producers:

- Default to `padding` field names prefixed with `_pad` so generated clients can hide them.
- When in doubt about whether a particular Rust layout has padding, emit the padding explicitly — it's always a no-op for Borsh-compatible layouts and correct for zero-copy layouts.
- Complex exotic layouts (hidden prefixes that carry version tags, sentinel-terminated arrays, non-LE numeric fields) combine `padding`, explicit [`number`](#102-explicit-number-types) forms, and the semantic type wrappers.

This means the type system describes **every wire layout** from Borsh through bytemuck through bespoke C-style structs without a separate `repr` or `serialization` hint — consistent with the design principle that wire layout lives in the type system (§ Design principles).

## 13. Contextual values (optional)

An optional layer on `IdlInstructionAccount.default` and `IdlInstructionArg.default`. Purely descriptive — minimal conformance ignores the `default` field entirely. Producers that want richer client generation may opt in.

### `IdlDefaultValue`

Tagged on `"type"`. Open vocabulary; consumers that don't recognize a type should ignore the hint.

| `"type"`         | Fields                                                                                     | Description |
|------------------|--------------------------------------------------------------------------------------------|-------------|
| `"payer"`        | _(none)_                                                                                   | Transaction fee payer. |
| `"identity"`     | _(none)_                                                                                   | Current wallet / signer identity. |
| `"programId"`    | _(none)_                                                                                   | The enclosing program's id. |
| `"accountBump"`  | `account: string`                                                                          | Canonical PDA bump for the named account. |
| `"pda"`          | `name: string`, `bindings?: { [seedName]: IdlDefaultValue }`                               | Reference a top-level PDA. `bindings` fills named variable seeds with any `IdlDefaultValue` (not just path expressions — full Codama `pdaSeedValueNode` parity). |
| `"account"`      | `name: string`                                                                             | Another account's address. |
| `"argument"`     | `path: string`                                                                             | An argument value. |
| `"constant"`     | `value: <literal>`, `valueType: IdlType`                                                   | Inline literal. |
| `"publicKey"`    | `value: string`, `identifier?: string`                                                     | A specific pubkey. `identifier` is a human-readable name for a well-known address (e.g. `"mplTokenAuthRules"`). Matches Codama's `publicKeyValueNode`. |
| `"resolver"`     | `name: string`, `dependsOn?: IdlDefaultValue[]`                                            | Named client-side resolver function. `dependsOn` lists the values the resolver needs to compute its output — matches Codama's `resolverValueNode.dependsOn`. |
| `"conditional"`  | `condition: IdlDefaultValue`, `value?: IdlDefaultValue`, `ifTrue?: IdlDefaultValue`, `ifFalse?: IdlDefaultValue` | Predicate-driven default. If `value` is provided, the condition matches when `condition` equals `value`; otherwise the condition is a truthy check on `condition`. `ifTrue` / `ifFalse` are chosen accordingly; either may be omitted (meaning "no default in that branch"). Matches Codama's `conditionalValueNode` — used extensively in mpl-token-metadata for pNFT-aware defaults. |

```json
{ "type": "pda", "name": "counter" }
```

## 14. Semantic type wrappers (optional)

Wrap any type with a semantic format (§11) without changing its wire encoding.

```json
{ "type": "semantic", "inner": "u64", "format": { "type": "amount", "decimals": 6, "symbol": "USDC" } }
```

| Field    | Type                    | Default | Description |
|----------|-------------------------|---------|-------------|
| `inner`  | `IdlType`               | —       | Wire type (unchanged). |
| `format` | `IdlSemanticFormat`     | —       | Rendering hint. |

Wire-identical to `inner`. Consumers may ignore the wrapper.

## 15. Compatibility notes

| Framework | Status | Notes |
|-----------|--------|-------|
| Anchor    | v1.0.0 superset of v0.1.0 shape | Discriminators move inline as leading [`constant`](#9-dispatch-and-constant-fields) fields on args/data (§9), `address`-as-expression (§12), flattened composite accounts (§5.2 with `group`), PDAs moved to top-level (§4). See [§16](#16-migration-notes). |
| Quasar    | Expressible in v1.0.0 | Quasar's `argsLayout: "fixed" \| "compact"` is expressed via the type system (no explicit tag needed — `shortU16` + CountNode wrappers cover both). `hasRemaining` → `remainingAccounts: {}`. `prefixBytes` → `count.prefix`. `maxLength` is *not* encoded (v1.0.0 type system describes the wire, not size bounds); a `{ "type": "semantic", "format": { "type": "raw" } }` carrier could be used for bounds hints but isn't required. |
| Codama    | Full parity (wire layout + instruction behavior) | **No `discriminators` field**: byte/field dispatch is a [`constant`](#9-dispatch-and-constant-fields) field inline with the args or data struct — one less dedicated concept, inline layout-and-dispatch. Size dispatch uses `IdlAccount.size`. First-class PDAs (§4, with `programId` seed variant), contextual values (§13) including `conditional`, `publicKey` with identifier, and `resolver` with `dependsOn`, semantic formats (§11), multi-program roots (§3). Layout wrappers (§10.4): `fixedSize`, `hiddenPrefix`, `hiddenSuffix`, `preOffset`, `postOffset`, `sentinel`, `zeroableOption`, `remainderOption`, `sizePrefix`, plus explicit-size `boolean` and field-level `padding`. Instruction-level: `optionalAccountStrategy`, per-tail `remainingAccounts` with `value: IdlDefaultValue`, `byteDeltas` (§5.7), `signerOptional` on accounts (Codama's `isSigner: "either"`), `defaultValueStrategy` on args (Codama's `omitted`/`optional` distinction). Sub-instruction dispatch (Codama's `createSubInstructionsFromEnumArgsVisitor`) is expressed by emitting each variant as a top-level instruction with layered constant fields — see [§9](#9-dispatch-and-constant-fields). v1.0.0 adds message-signer authorization (§5.6), which Codama does not model. Codama-only concepts not ported (codegen concerns, not IDL shape): `linkOverrides` to `"hooked"`, visitor pipeline internals, `setNumberWrappersVisitor` (we provide the shape via the `semantic` type wrapper, not the transform). |

## 16. Migration notes

Breaking changes from v0.1.0.

| Change | v0.1.0 | v1.0.0 | Migration |
|--------|--------|--------|-----------|
| Discriminators | `discriminator: number[]` on instruction/account/event | inline as a leading `{ "type": "constant", "bytes": [...] }` field in `args` / `data.fields` | Prepend a constant-typed field to the args or data struct. No separate `discriminators` field. |
| Remaining accounts | implicit | `remainingAccounts?: { shape? }` | Emit `remainingAccounts: {}` when accepted. |
| Address expressions | `address: string` only | `address: { type: "constant" \| "field", ... }` | Wrap literal pubkeys in `{ "type": "constant", "value": "..." }`. |
| `relations` | `relations: string[]` | removed — use `address: { type: "field", path }` | See [#4421](https://github.com/solana-foundation/anchor/issues/4421). |
| PDAs | inline on each account | top-level `pdas[]`; accounts use `default: { type: "pda", name }` | Extract unique seed sets; dedupe. |
| Account layouts | name-matched against `types[]` | inline `data: struct` on `IdlAccount` | Inline the referenced struct. |
| Event layouts | name-matched against `types[]` | inline `data: struct` on `IdlEvent` | Inline the referenced struct. |
| Constants | top-level `constants[]` | removed — inline at point of use | Delete. |
| Serialization | `serialization: "borsh" \| "bytemuck" \| ...` | removed — express via type system | Delete. |
| Repr | `repr: { kind: "rust" \| "c" \| "transparent", packed, align }` | removed — express via type system | Delete. |
| Error message field | `msg?` | `message?` | Rename. |
| Number types | `"u64"` only | `"u64"` is LE shorthand; non-LE uses `{ type: "number", format, endian }` | No-op unless emitting non-LE. |
| Array / Vec | `{ vec: T }`, `{ array: [T, N] }` | unified: `{ type: "array", value: T, count: IdlArrayCount }` | Rewrite containers. |
| Deployments | all four keys required, `null` for missing | omit missing keys | Remove `null` entries. |
| Generator provenance | absent | `metadata.generator: { name, version }` required | Fill in. |
| Type def tag | `type: { kind: "struct" \| "enum" \| "type" }` | `shape: { kind: "struct" \| "enum" \| "alias" }` — `"type"` variant renamed to `"alias"` | Rename. |
| Enum variant body | untagged `IdlDefinedFields` (Named \| Tuple) | tagged `body: { kind: "empty" \| "tuple" \| "struct" }` | Wrap. |
| Composite accounts | nested `IdlInstructionAccounts` groups | flattened with `group: string` tag | Inline children; preserve group label. |
